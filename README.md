# Replan 福岡 — 崩れても立て直せる旅程

福岡市内の旅行プランナーのプロトタイプです（デモ用サンプル）。

> 旅程を作る時点で、屋外の予定ごとに**屋内の代わり（Plan B）**を用意しておく。
> 当日に雨・遅れ・暑さ・疲れが起きたら、**変更前との差分と理由**を見せて、軽いものはワンタップ（または自動）で、重いものは必ず確認してから組み直す。いつでも元に戻せる。

- 対象: 福岡市内（天神・博多・中洲・大濠公園・百道浜・太宰府）／国内旅行をする大学生・20代の友人グループ
- スマホ表示が前提（モバイルファースト）。API キー不要。外部データはすべてサンプル／モック。LLM は呼びません（計算はルールベース）
- スポットの営業時間・位置・食事制限への対応などは**サンプルデータで、不正確な場合があります**（アプリ内にも明記）

## 当日の3つのモード（手動／提案／おまかせ）

当日モード（`/today`）の上部で切り替えます。**旅程ごとに保存**され、初期値は「提案」です。

| モード | 軽い変更（Optional・休憩・余白・Plan B・遅れの吸収など） | 重い変更（Must・標準・食事を外す／Must の入れ替え／固定時刻／予算超え／大きな変更） |
| --- | --- | --- |
| **手動** | 差分を見て確定（バナーは出さず、バッジだけ） | 差分を見て確定 |
| **提案**（既定） | ワンタップで反映（確認なし） | 差分を見て確定 |
| **おまかせ** | **自動で反映**して知らせる（トースト・履歴に「自動で反映」） | 差分を見て確定（**おまかせでも自動では反映しない**） |

- どの変更も**直前の10件まで「元に戻す」**でぴったり戻せます（履歴は旅程と一緒に保存）。
- **何かを削る・替える・ずらしたら、必ず理由が付きます**（「最終便（太宰府駅 16:30 の最終便）に間に合わせるため」「雨のため」「食事の時間帯に収めるため」など。`ExplanationWriter` が文章にします）。
- 「実績」（着いた・出発した）の記録は事実なので、軽ければ手動モードでも確認なしで記録します。

## 当日に起こせること（再計画のイベント）

`replan(旅程, イベント, ctx, {dayIndex, nowMin, removeMustIds})` が、すべてのイベントを同じ規則で扱います。

| イベント | 内容 |
| --- | --- |
| 雨 `plan-b` | 屋外の予定を Plan B（屋内）に替える。雨の強さは小雨／本降り／強い雨。許容度ごとの通知しきい値あり |
| 暑さ `plan-b`（cause=heat）・`heat-rest` | 暑さ指数（WBGT）28以上で「Plan B に替える」か「屋外の後に15分休憩」、31以上は屋外を Plan B に |
| 遅れ `delay` | 余白が先に吸収（いま余白の最中なら、その残りが吸収）。足りない分は Optional → 滞在短縮 → 標準 の順で削る |
| 臨時休業 `closure` | 代わりの候補に替える／スキップ。食事の店は、食事制限に対応できる店だけから替える |
| 疲れた `tired` | 少し＝30分の休憩、かなり＝60分の休憩＋Optional のスキップ＋近い順の並べ替え。いま滞在中の休める場所なら、そこで延長 |
| 固定時刻 `fixed-add` / `fixed-remove` / `fixed-move` / `margin` | 最終便・予約などを守る。出発すべき時刻を逆算。現在時刻より前の時刻は追加しない |
| 着いた／出発した `progress` | 実際の進み具合を記録し、遅れ・早まりを後ろの予定に反映。早く進んだら提案を出す（自動では変えない） |
| 寄り道 `detour` | 近く（1km以内）の営業中のスポット、または自由入力。エンジンは寄り道を自動では削らない |
| 余白・延長 `add-buffer` / `extend-stay` / `add-spot` / `add-rest` / `skip` / `restore` | 早く進んだときの提案などで使う |

**組み直しの優先順位（高い順）**: 固定時刻 ＞ Must ＞ 食事 ＞ 休憩 ＞ 標準 ＞ Optional（余白は遅れを吸収する材料として最初に縮む）

言葉からイベントへの変換は `EventParser` の interface（`core/parser.ts`）です。いまは「疲れた・雨・遅れ・寄りたい」のキーワード実装で、LLM に差し替えられます（差し替えポイントは `src/eventParser.ts`。LLM は呼んでいません）。

## グループで計画する（`/group`）

2〜6人の希望を**1台の端末を回して**集め、3つの案から投票で決めます。トップ画面の「グループで計画する」から入ります。

1. **準備**: メンバー（名前・主催者）と候補日（2〜4日）を入れる。
2. **回答**: 1人ずつ「参加できる日・予算の上限（円）・食事制限・雨・ペース・好み（好き／どちらでも／苦手）・行きたい場所（2件まで）」を入力。一覧には「回答済み」の進み具合だけが出ます（**予算の金額と「苦手」は、本人の入力画面でだけ見えます**）。
3. **まとめ**（`aggregatePreferences`）: 日程＝全員の共通日（なければ最多人数の日と欠席者）／予算＝最小／食事制限＝和集合（食事は必ず守る）／雨＝いちばん慎重／ペース＝中央値（偶数で割れたら遅いほう）／好み＝好き+2・どちらでも0・苦手−3の合計／行きたい場所＝2人以上の希望を先に Must、全員が最低1件入るよう各人の第1希望を足す。**調整したポイントが、1行ずつ理由つきで出ます**。
4. **3つの案**: バランス案（いちばん不満な人の満足度が最大）／合計いちばん案／移動いちばん少ない案。メンバーごとの満足度（0〜100）と理由、予定ごとの「誰の希望か」のアイコンが付きます。どの案でも誰かが40未満のときは「希望が大きく割れています」と出ます。
5. **投票**: 1人1票、全員が投票するまで結果は見えません。同票なら主催者の票で決まります。決まったら「この案で旅程を確定する」で、ふつうの旅程（当日モードも使える）になります。

個人の予算額・「苦手」は、集約結果・満足度の理由・共有リンク・保存される旅程に含まれません。ただし**端末の localStorage には全員の回答がそのまま入ります**（画面上の約束で、暗号化はしていません）。

## デモシナリオ

1. **A（雨）**: トップ画面の初期値がデモ設定（**友人・普通の予算・グルメとカフェ・ゆったり・小雨OK・日帰り**）。旅程をつくる → 当日モードで **13:00** → 🧪 デモ操作パネルで **「雨が降り出す」** → 「Plan Bに切り替えますか？」→ 「残りすべて切り替える」→ 提案モードなら軽い変更なのでワンタップで反映、**理由（雨のため）つきの差分**と「元に戻す」が出る。電車の遅延・臨時休業・共有リンク・並べ替えも試せます。
2. **B（固定時刻と疲れた）**: Must に「太宰府天満宮」「九州国立博物館」を選び、固定時刻で最終便を登録（サンプルの 18:05、または自分で 16:30 に）。当日 14:30 に **60分の遅延** → 標準の予定を外す重い変更なので確認が出て、**削られた予定の理由が「最終便に間に合わせるため」**と出る。「疲れた」→「かなり疲れた」で休憩が入り、歩行距離が減る。メンバー限定の固定時刻（Cさんだけ 17:00）も試せます。
3. **C（グループ）**: 4人（A グルメ好き・自然が苦手・¥8,000／B 自然・詰め込み・¥15,000／C カフェとアート・屋外なし・¥10,000／D こだわりなし・ゆったり・¥12,000）で入力 → 調整ポイント → 3案 → 投票 → 確定 → 当日の遅れ（おまかせで自動反映 → 元に戻す）と雨（Must の屋外は確認 → 元に戻す）。
4. **D（当日の出来事）**: 太宰府の旅程で「出発した」を20分遅れで押す → 後ろが遅れる → 「ここに寄る」で寄り道 → 暑さ（WBGT 31）で屋外の予定の対応 → 「少し休みたい」でいま滞在中のカフェの滞在が延長される → 早く進んだら提案が出る（自動では変わらない）。

`npm run demo:e2e` は A・B・C・D に加え、3モード（M）、壊れたデータ（H）、グループ（G）を自動で最後まで通して確認します。

### 旅程生成アルゴリズム（`core/planner.ts`）

LLM は使わず、ルールベースです。

1. **ペース設定**: ゆったり＝1日の開始が遅く・スポットは少なめ（目安3）・滞在 ×1.25・余白 45分×最大3 ／ 普通＝4・30分×2 ／ 詰め込み＝6・滞在 ×0.85・15分×1。余白が遅れを吸収して縮められる下限は 20／10／5分。
2. **スコアリング**（`scoring.ts`）: 興味一致（主カテゴリ +3.0、タグ +1.2）＋人気度、予算超過の減点、同行者との相性、雨許容度による屋外の減点。同じ日の同カテゴリの連続・混雑時間帯・長すぎる移動・すでに行ったエリアへの戻りは減点。直前と同じエリアは加点。
3. **Must** はエリア単位で日に割り当て、強く優遇して必ず入れる。入れられなければ警告（黙って落とさない）。**行きたい店（Must の食事向けスポット）は、食事の枠で使う**。
4. **時間を先に進めながら貪欲に配置**。営業時間内に収まること・移動時間・日の終了時刻を守る。**昼・夜の食事枠**（ランチ 11:30〜13:45 開始／ディナー 17:30〜19:30 開始）を確保し、食事は食事向けスポットだけ・**食事制限があれば、全員の制限に対応できる店だけ**。夜景は日没後に置く。
5. **歩行距離**: ペース別の目安（5/8/12km）の85%に収まるよう、歩行の予算と減点を変えて何通りも作り、空きが少なく食事が揃うものを選ぶ。その後、動線を改善（2-opt）。
6. **移動時間**は直線距離×1.3 を道のりとみなし、1km以下は徒歩、それ以外は公共交通で概算（`core/geo.ts`）。
7. Must 以外のスポットのうち、スコア下位 1/3 を **Optional** にする。

> ラベルは Must / Optional / 余白 に加えて **「標準」** を追加しています。Must 以外がすべて Optional になると「余力があれば」の意味が薄れるためです。

### Plan B（`core/planb.ts`）

屋外・半屋外のブロックごとに、**屋内**・元のスポットから**2km以内**・ブロックの**開始時刻にそのまま入れる**・**興味カテゴリが近い**ものを選びます。食事向けの店は食事制限に対応できるものだけ。旅程内の他のスポット・他ブロックの Plan B とは重複させません。見つからなければ `planB: null` にして警告を出します。

### 再計算（`core/schedule.ts`）

- 開始済みのブロックは固定。各ブロックの開始 = `max(前の場所からの到着, 計画上の開始, 遅れによる下限)`。実績（着いた・出発した）があれば、それを優先します。
- **遅れ**は最初の未開始ブロックの開始に加算。**余白ブロックが先に縮んで**（下限はペース別）吸収し、吸収しきれない分だけ後ろへ押し出される。
- **固定時刻ブロックの開始は固定時刻そのもの**。手前のブロックには、固定時刻から逆算した「最遅の開始時刻」を持たせる（間に合わなければ `fixed-missed` と不足分を記録）。
- 営業時間外・食事の窓・終了予定時刻（30分の許容あり）の超過を検出。

### 再計画エンジン（`core/replan.ts`）

結果は「提案」で、元の旅程は変えません。時間が足りないときは次の順で処理します（違反が解消するまで）。

1. 動かせるものを整える（近い順の並べ替え＝かなり疲れたのとき）
2. **Optional を後ろから削除** → 3. **各スポットの滞在時間を短縮**（食事以外。最低滞在まで）→ 4. **標準の予定を後ろから削除**
5. **食事は削らず**、時刻・滞在・店の差し替え（元の店から1km以内。食事制限に対応する店だけ）で調整
6. それでも足りなければ、**Must・食事・寄り道は「削る候補」として提示するだけ**（勝手に削らない）。ユーザーが選めば外して組み直す

### 固定時刻（`core/fixed.ts`）

- **出発すべき時刻 = 固定時刻 − 移動時間 − 余裕時間**（余裕時間の初期値は10分）。出発すべき時刻の **30分前・10分前**に通知。固定ブロックは鍵アイコン付きで**ドラッグできず**、固定時刻をまたぐ並べ替えも拒否します。
- **メンバー限定の固定時刻**（例:「Cさんだけ 20:30 の電車」）: グループの旅程は動かさず、Cさんが抜けたあとの予定を **「Cさん不在」** と表示します。
- サンプルの最終便: 太宰府駅 18:05 の電車／太宰府天満宮前 19:20 の最終バス／筑前前原駅 20:10 の電車。**実在の時刻表ではありません**。

### 「疲れた」ボタンと歩行距離

- **少し休みたい**: 次の予定の前に、近く（800m以内）の屋内の休める場所で**30分**の休憩（いま滞在中の休める場所なら、そこで延長）。**かなり疲れた**: **60分**の休憩（500m以内）＋残りの Optional をスキップ＋近い順に並べ直し＋以降は徒歩を短く見積もる。徒歩20分以上の移動には、公共交通・タクシーを提案。
- どちらも **Must・食事・固定時刻は守ります**。グループには「メンバーの1人が休憩を希望しています」とだけ出し、押した人の名前は出しません。
- **推定歩行距離**のペース別の目安は **5km／8km／12km**。次の予定まで行くと目安を超える見込みのとき、「次の予定の前に休憩を入れますか？」と提案します。

### 当日モードの雨・暑さの判定

- 雨への許容度ごとの通知しきい値（降水確率）: **屋外NG 30%** ／ **小雨ならOK 60%** ／ **気にしない 通知なし**（手動の切り替えは常に可能）。強さ（小雨・本降り・強い雨）の許容も見ます。
- 暑さ指数（WBGT）: 28以上＝厳重警戒、31以上＝危険。11〜16時に重なる**屋外**の予定が対象（`HEAT_RULES` で調整）。

## 前提・制限

- 旅行日は、通常の入力では「直近の土曜（と日曜）」で固定です。グループでは候補日を指定します。
- 1日目は博多駅から、2日目は宿泊先（天神）から出発する前提です。宿泊先や帰路の移動は扱いません。
- 共有リンクは旅程の内容を URL に含めます（スポットは id のみ、8KBまで）。受け取り側も同じスポットデータを持っている前提です。
- 当日モードの「現在時刻」はデモ用に操作します。実時刻・位置情報には連動しません。暑さ・雨の予報はモックです。
- 3案の違いが小さいことがあります（行きたい場所が多い日など）。夕方に開く店を希望にすると、午後に長い余白が出ることがあります。
- グループの回答は端末の localStorage にそのまま保存されます（画面上の約束で、暗号化・ログインはしていません）。食事制限の対応は仮データです。
- 保存形式は v3 です。旧版（v2）は読み込み時に変換します。読めない保存データは、確認のうえで削除するかバックアップに退避します。
- やらないこと: ログイン・決済・予約、複数端末の同期・通知、実際の API 呼び出し、LLM の呼び出し、自前の地図表示・ナビ（Google Maps へのリンクで代用）、グループの割り勘・精算、位置の共有、旅の記録。
