# 設計判断の記録（改善指示書 v1）

形式: **選んだ解釈** ／ 理由 ／ 代替案。

## フェーズ1: 旅行として不自然な組み直しを直す

### 1-1. 保護の優先順位と、削減の順序
- **選んだ解釈**: 守る順は 固定時刻 > Must > 食事 > 休憩（「疲れた」で入れたもの）> 標準 > Optional。余白は遅れの吸収材として最初に縮む。
  削る順は 余白（再計算で自動）→ Optional（後ろから、効果のあるものだけ）→ 滞在短縮（食事以外）→ 標準（後ろから、食事以外）→ 食事の調整 → Must・食事の「削除候補」提示（自動では削らない）。
- 理由: 指示書 §1.1 のとおり。「余白を下限まで縮める」は、`recomputeDay` が遅れを吸収する過程でもともと行っているので、独立したステップにはせず、`minBufferMin`（ゆったり20／普通10／詰め込み5分）を渡す形にした。
- 余白の下限は「元の長さと下限のうち短いほう」とした（15分だけ待つ余白を、ゆったりの下限20分に引き延ばさないため）。
- 代替案: 余白の縮小を `steps` に明示する。差分表示（`buffer-changed`）に出ているので見送った。

### 1-2. 食事（`meal` 属性と窓）
- **選んだ解釈**: `Block.meal?: "lunch" | "dinner"` をラベルとは別に持つ。食事の店が Must のこともあるため（Must かつ食事）。
- 窓は2種類に分けた。
  - 調整の窓（`MEAL_ADJUST_WINDOW`）: ランチ 11:00〜14:30／ディナー 17:00〜21:00。開始が窓の開始以降、終了が窓の終了以前。違反は `outside-meal-window`（重い違反）。
  - 生成時の目標の窓（`MEAL_WINDOW`、従来どおり 11:30〜13:45／17:30〜19:30 に開始）: 変更なし。生成では、食事が調整の窓の終わりまでに終わることも条件に加えた。
- 食事の調整は 窓の中で時刻をずらす（再計算で自動）→ 最低滞在まで短縮 → 元の店から1km以内の、同じ食事枠の別の店に差し替え → Must と同じ「削除候補」。差し替え先は、旅程内で未使用・休業でなく・営業中のもの。
- 食事は削除しない。標準の削除（③）・Optional の削除（①）の対象から外した。
- 代替案: 食事を標準扱いにして最後に削る。指示書は「削除しない」ので採用しなかった。

### 1-3. 太宰府の食事とデータ
- **選んだ解釈**: `梅ヶ枝餅 かさの家` は `snack: true`（軽食）にし、`mealSlots` を外した。通常のスポットとして立ち寄る。
- 太宰府に食事向けスポットを2件追加した（実在の店。Web検索で店名・住所・営業時間・定休日を確認した）。
  - さいふうどん 木村製麺所（太宰府市宰府3-4-31、11:00〜16:00、火曜定休、駅から徒歩約3分）
  - お石茶屋（太宰府市宰府4-7-43、10:00〜16:30、不定休、本殿裏の食堂）
- 座標・混雑時間帯は概算。営業時間は検索結果によるが、変更されうる。`Spot.dataNote` に概算の旨を持たせ、スポット詳細（`BlockDetailSheet`）に表示する。
- 店名はいずれも実在を確認したが、座標は住所からの目分量であり、地図で確認していない。
- **サンプル数**: 40件 → 42件。初回仕様の「30〜40件程度」から外れるため、テスト（`planner.test.ts`）の上限を 45 に変更した。
- 検討して外した候補: やす武（参道の蕎麦店）。2024年12月に食事提供を終え、別の場所の「蕎麦 安武」に移ったという情報があり、位置と営業が不確かなため。

### 1-4. 休憩場所（`restable`）と、休憩の位置
- **`restable` の付け方**: 屋内で座って休める施設に true（カフェ4、商業施設・地下街、美術館・博物館、福岡タワー、蔦屋書店）。小さな史料館・歴史的建物（赤煉瓦文化館・貴賓館・博多町家・福岡城むかし探訪館・宝物殿）と、食事の店は false にした（休憩の場所に使うと、食事の枠や小さな施設の占有になって不自然なため）。半屋外のキャナルシティは、休憩場所は屋内に限る方針のため false。計14件。
- **休憩の位置**: 次の予定の手前／次の予定の後／次の次の予定の後（最終便のあとには入れない）の3候補を、実際に組み直して比べる。選ぶ基準は ①解消できる案 ②失う予定の重みの合計が最小（Optional=1・標準=3・食事=10・Must=100、短縮は分あたり0.01） ③同点なら早い位置。
- **「今いる場所での延長」の扱い**: 指示書は最優先と書いている。実装では、休憩場所の探索で「直前の場所」が距離0で最も近い候補になるため、今いる場所が休める屋内なら必ず選ばれる。位置の比較では同点なら早い位置（＝延長）が勝つ。ただし、延長すると予定を失い、位置を変えれば失わずに済むときは、位置を変える（受け入れ条件「かなり疲れたで、休憩位置を変えれば削らずに済む予定は削られない」を満たすため）。
- 延長は、元のブロックの滞在を伸ばすのではなく、**同じ場所に `rest` ブロックを直後に置く**形で表した。休憩ブロックは保護される（短縮・削除されない）ので、あとの削減で延長が消えない。画面には「ここで休憩を延長」と出る（`restKind`）。
- 休憩に使える場所は、旅程内で使用済みでもよい（これまでに行った場所・今いる場所）。ただし、これから行く予定のスポット（休憩より後ろ）と休業のスポットは使わない。

### 1-5. 最終便の前の長い空き
- **空きの定義**: 出発すべき時刻（固定時刻 − 移動 − 余裕）− 空きが始まる時刻（直前の予定の終わり。当日モードでは現在時刻以降）。直前の「予定」には休憩を含め、余白（buffer）は含めない（余白は空きそのものなので）。
- **提案の出す条件**: 組み直し後に60分以上で、組み直し前より広がったとき（`suggestForGap`）。固定時刻を追加した直後も、前は最終便がなく空きが0なので対象になる。UI は、確定された旅程に対して `suggestionsForDay` で出すこともできる。
- 提案は3種類。選ぶと新しい組み直し案（提案→確定）になる。
  - 早い便で帰る: 新イベント `fixed-move`。サンプルの前の便は `FIXED_EARLIER_SERVICES`（太宰府駅 15:35／16:35／17:05／17:35、天満宮前バス停 17:20／18:00／18:40／19:00、筑前前原駅 18:10／18:40／19:10／19:40。実在の時刻表ではない）。いまの予定をすべて回って間に合う便のうち、いちばん遅い便といちばん早い便の最大2件を出す。
  - 近くで Optional を足す: 新イベント `add-spot`。直前の場所から1km以内、未使用の非食事スポットで、最終便に間に合うもの。スコア最大の1件。
  - 駅の近くで待つ: 新イベント `add-rest`。最終便の場所から800m以内の、屋内の休める場所。30〜90分。
- 自動では反映しない。提案カードに「この案で組み直す」ボタンを出し、押すといまの案を確定したうえで、その提案の新しい案を作る。

### 1-6. 生成時の歩行距離（目安の85%以内）
- **選んだ解釈**: 日ごとに、まず制約なしで生成し、推定歩行がペース別の目安の85%を超えるときだけ、複数の組み直し（歩行1kmあたりの減点 × 歩行の予算）を試す。目安に収まるもののうち、コストが最小のものを採用する。
  コスト = 空き時間（ペースの余白より長い分）＋ 食事の抜け×120 ＋ Must の抜け×2000 ＋ 手を入れすぎた分（減点の強さ×0.5）＋ 屋外が2件に満たない分×30（屋外NGでない場合）。目安を超えるものは +1000。
  どれも収まらないとき（Must が重いなど）は、コストが最小のものを使う（Must は落とさない）。
- 歩行の予算（貪欲法の中で、これまでの歩行 + そのスポットの歩行が予算に収まるスポットだけを選ぶ）と減点は併用する。減点だけだと日の後半が空きすぎ、予算だけだと食事が入らなかった。
- エリアの再訪にも減点（スポット2.0・食事1.0）を加えた。貪欲法が博多⇄天神を何度も往復するのを抑えるため。
- 副作用（正直な記録）
  - 目安5kmのゆったりでは、午後の屋外が1件（屋台）になる。以前は2件だった。歩行の推定が屋外の散策に多く配分されるため。
  - 午後に2時間前後の余白が残る日がある（普通ペースのデモなど）。歩行の予算を使い切ったあと、行ける候補がないため。
  - 日の途中に長い余白が残る問題は、生成側の限界として残る（§7 の弱点に追記する）。
- **`FILLER_GAP_MIN`**: 150 → 100 分に変更。次の食事までの空きが100分を超えるときは、ペースの上限を1つ超えてスポットを足す。
- 代替案: 目安の85%という数字を緩める。指示書の指定なので採らなかった。

### 1-7. 動線の改善（2-opt）
- **選んだ解釈**: 生成後の後処理として、食事・固定時刻・余白・休憩は元の位置に固定したまま、スポットの並び順の一部（連続する範囲）を逆順にする。
  採用の条件は、移動時間の合計とエリア再訪（1回を8分換算）の合計が3分以上減ること、営業時間・食事の窓の違反が増えないこと、夜景が17:30より前にならないこと、時間帯の適合（カフェは午後など）が大きく悪化しないこと、終了時刻が20分より遅くならないこと。
- 当初は移動時間だけを見たが、エリア再訪が増える入れ替えがあったため、再訪を条件に加えた。
- 代替案: 先にエリアを時間帯に割り当ててから順番を決める。生成の作りが大きく変わるため、後処理にした。

## フェーズ2: 確定ルールの統一と3つのモード

### 2-1. 3つのモードの意味と、「誰が気づくか／誰が決めるか」
- **選んだ解釈**: モードは `Itinerary.settings.mode`（`manual` | `suggest` | `auto`、省略時は `suggest`）として旅程ごとに保存する。当日モードと旅程画面の両方に切り替え（`ModeSwitch`）を置き、変更すると、元の旅程と当日の作業コピーの両方に反映する。共有URLには含めない（受け取る側の対応のしかたは、受け取る人が決めるため）。
- 「軽い変更は『ワンタップ』」は、**ユーザーが押したボタンそのものが1タップ**という意味に解釈した。雨のバナーの「切り替える」、シミュレーション操作の「遅延」、「疲れた」の段階の選択、旅程画面の余裕時間の変更などがこれにあたる。軽い変更なら、その場で反映して「元に戻す」を10秒出す。確認画面（差分→確定）は出さない。
- 確定のしかたは `decideApply(mode, weight)` の1本に統一した。重い変更はどのモードでも確認。軽い変更は、手動なら確認、提案・おまかせならそのまま反映。タップなしの自動反映は `canAutoApply`（おまかせモードの軽い変更だけ）で、いまは雨の Plan B 切り替えと、歩行距離が目安を超えそうなときの休憩（軽い変更なら）が対象。
- 手動モードでは、バナー（雨・休業・歩行距離・出発の通知）を出さず、小さなバッジに置き換える。**出発の30分前・10分前の通知もバッジにした**（「自動検知のバナーを出さない」に合わせた。ただし、バッジを押すまで気づけない弱点がある）。バッジを押すと、その対応の案（差分）が出る。
- おまかせモードで重い変更が出る場合（雨で Must の屋外を切り替える、など）は、自動では反映せず、提案モードと同じバナーで確認を求める。

### 2-2. 変更の重さの分類（`classifyChange`）
- 軽い: 時刻のずれ・余白の伸縮、Plan B への入れ替え、Optional のスキップ、休憩の挿入、滞在の短縮。
- 重い（理由を画面に出す）:
  1. 標準・食事・Must が外れる（スキップ・休業・外した）。**Must を別のスポットに入れ替える**のも重い（Plan B・休業の代替でも）。
  2. 固定時刻の追加・変更・削除（`fixed-add` / `fixed-move` / `fixed-remove`）。余裕時間の変更そのものは軽い（固定時刻そのものは変わらないため）。余裕時間を変えたせいで予定が外れる場合は、外れる予定のほうで重くなる。
  3. 追加の費用: 新しく入るスポット（入れ替え・追加）の価格帯が、予算の「気にせず選べる上限」を超え、かつ元より高いとき。タクシーの提案を採用する操作はまだ無いので、タクシーはこの分類の対象外（提案の表示のみ）。
  4. 予定の半分以上が変わる: Must・標準・Optional・食事のうち、内容が変わった予定（入れ替え・スキップ・休業・外す・並べ替え・短縮）が、2件以上かつ半分以上。**時刻が動くだけの予定は数えない**（「時刻のずれの反映」は軽い変更と明記されているため）。
  5. 間に合わない予定が残る案（`!feasible`）と、Must・食事を外す候補が出る案は、自動では確定しない（重い）。
- 食事の店の差し替え（食事の調整⑤、Plan B で食事が入れ替わる）は、いずれも軽いとした。ただし価格帯の条件には当てはまる。理由: 雨のデモで夕食（屋台）が Plan B に替わることが多く、これを重くすると「雨はワンタップ」が成り立たないため。
- 軽いものと重いものが混ざる場合は全体を重い変更とする（理由が1つでもあれば重い）。
- 副作用の修正: 雨で夕食が「水たき 長野」（高価格帯）に切り替わると、費用の理由で重くなりデモが成り立たなくなったため、Plan B の予算超過の減点を 0.7 → 1.5/段階（旅程生成の予算の重みと同じ）に強めた。予算内の別の店があれば、そちらが選ばれる。

### 2-3. 元に戻す
- **選んだ解釈**: 反映のたびに、反映前の旅程の複製（`ChangeSet.before`）を履歴に積む。「元に戻す」は直前の履歴1件を巻き戻す（連続して最大10件）。完全一致はテストで確認している。トースト（10秒）と、変更履歴のボタンの両方から戻せる。
- 履歴は、当日モードでは `TodayState.history`、旅程画面では `TripState.history`（最大10件）。旅程画面の並べ替え・メンバー変更も履歴に入る。
- 旅程が実際に変わらない組み直し（差分も設定の変更もない）は、反映せず履歴にも残さない。余裕時間の変更のように、差分には出ないが設定が変わるものは、履歴に残して戻せる。
- 巻き戻し以外の履歴の編集（途中の1件だけを取り消す）は、前後の整合が取れないので対応しない。
- 代替案: 差分の逆適用で戻す。再計画が副作用（Plan B の付け直しなど）を持つので、スナップショットのほうが確実。保存サイズは増える（旅程1つ約10〜15KB × 10件）。

### 2-4. 雨の強さ
- 基準は `RAIN_RULES`（`src/core/weather.ts`）1か所: 屋外NG は 0.5mm/h 以上または降水確率30%以上、小雨ならOK は 3mm/h 以上（降水確率は見ない）、気にしない は 10mm/h 以上のときだけ提案。
- デモ操作の雨の強さは、小雨（60%・1mm/h）、本降り（80%・5mm/h、初期値）、強い雨（95%・15mm/h）の3段階。
- 古い保存データ（降水確率だけで雨量がない）は、降水確率から雨量を見積もって読む（`rainMm`）。
- 「気にしない」は、従来は自動の提案が一切なかったが、強い雨のときだけ提案するように変えた（指示書どおり）。手動の切り替えはいつでもできる。
- 変更したテスト（`today.test.ts`）: 雨の通知条件を、降水確率のしきい値から、雨量・降水確率・許容度のルールに書き換えた。

### 2-5. 変更の理由（cause）
- 理由の種類は `fixed:<id>` / `closing:<spotId>` / `closure:<spotId>` / `meal-window` / `day-end` / `rest` / `tired` / `rain` / `heat` / `delay` / `detour` / `user`。指示書の一覧に、`meal-window`（食事の窓に収めるため）、`tired`（疲れたため）、`user`（ユーザーの操作）を足した。`heat`・`detour` は型だけ用意し、フェーズ3で使う。
- 削減の理由は、**その手順で解消した問題**から求める（`resolveCause`）。例: 光明禅寺の閉館に間に合わせるために手前の予定を削ったなら `closing:光明禅寺`、最終便に間に合わせるために削ったなら `fixed:<id>`。休憩を入れて後ろの予定がずれたときは `rest`。
- 文章は `ExplanationWriter`（`explain(cause, ctx, itin)`）が作る。いまはテンプレート（`templateWriter`）で、`replan` のオプション `writer` で差し替えられる。差分の各項目に、`cause` と `reason`（文章）を持たせた。
- 例: 「最終便（太宰府駅 18:05 の電車（最終））に間に合わせるため」「「光明禅寺」の閉館（16:30）に間に合わないため」「休憩を入れたため」。
- 画面: 提案カード・変更履歴の差分の各項目に「理由：…」を出す。

### 2-6. 変更したテスト・E2E
- `today.test.ts`: 雨の通知条件の書き換え（2-4）。差分の比較は、理由の項目を除いて比べる。
- `scripts/e2e-demo.mjs`: シナリオAは「雨→案→確定」から、「雨→ワンタップで反映→元に戻す→もう一度反映」に変更。遅延と、疲れた（かなり疲れた）も、提案モードでは軽い変更としてそのまま反映されるので、確定ボタンを押す手順を、反映の確認に変更した。「少し休みたい」は、手動モードで案→取り消しを確認する形にした。シナリオM（3つのモード）を追加。
- 旧 `isQuietChange`（確認なしで反映する例外）は廃止し、`classifyChange` に統一した。固定時刻を外す操作は、問題が出なくても確認になる（固定時刻が絡むため）。

### 2-7. 既知の弱点（フェーズ2時点）
- 手動モードでは、出発の通知もバッジになるため、見逃しやすい。
- タクシーの提案を採用する操作がないため、費用の分類はスポットの価格帯のみ。
- 自動反映の対象は、雨と歩行距離の休憩だけ。遅れ・暑さなどの自動検知はフェーズ3。
- 履歴は旅程のスナップショット（最大10件）なので、localStorage の容量を使う。
