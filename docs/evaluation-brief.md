## 1. 概要

**コンセプト**: 「崩れても立て直せる旅程」。旅程を作る時点で、屋外の予定ごとに屋内の代わり（Plan B）を用意しておき、
当日に雨・遅延・臨時休業・疲れなどが起きたら通知し、**差分を確認して確定**することで立て直せる。

- 対象: 福岡市内（天神・博多・中洲・大濠公園・百道浜・太宰府）、国内旅行をする大学生・20代の友人グループ。スマホ表示前提。
- 制約: API キー不要（外部データは adapter 層でモック）、データ保存は localStorage、サーバー・DBなし、LLM不使用（旅程生成はルールベースで差し替え可能な関数）。
- 技術: Next.js 16（App Router）/ React 19 / TypeScript 5.9 / Tailwind 4 / Vitest 5 / dnd-kit / playwright-core（E2Eスクリプトのみ）。
- 規模: `src/core` 3,333行（純粋ロジック）、`src/components` 2,736行、`src/app` 834行、`tests` 1,500行（117テスト）、`scripts/e2e-demo.mjs` 402行。
- 起動: `npm install && npm run dev` → http://localhost:3000（スマホ幅で見る）。`npm test`（117件）、`npm run demo:e2e`（ブラウザでデモを自動確認）。
- 画面: `/` 入力（6問＋Must任意）、`/itinerary` 旅程（ドラッグ並べ替え・固定時刻・メンバー）、`/today` 当日モード、`/share?s=…` 共有（閲覧専用）。

### スポットデータ（サンプル）
40件（天神10・博多7・中洲4・大濠8・百道浜4・太宰府7）。屋内24・屋外12・半屋外4。カテゴリはグルメ7・カフェ4・歴史13・自然4・ショッピング7・アート3・夜景2。
食事枠に使えるのは7件（`mealSlots`）。**名称は実在だが、座標・営業時間・定休日は記憶ベースの概算**で不正確な可能性がある（画面にも「サンプルデータです」と明記）。
糸島のスポットは含まない（固定時刻の最終便の例として「筑前前原駅」があるのみ）。

## 3. アーキテクチャ

```

    types.ts       Spot / Block / Day / Itinerary / FixedEvent / Member …
    planner.ts     generateItinerary（ルールベース）
    scoring.ts     スコア・カテゴリ近接度
    planb.ts       Plan B 選定・付与（旅程内で重複しない）
    schedule.ts    recomputeDay（時刻再計算・固定時刻の逆算）
    replan.ts      replan（再計画エンジン）・describeEvent・isQuietChange
    fixed.ts       固定時刻（逆算・メンバー不在・通知・サンプル最終便・メンバー初期値）
    walking.ts     推定歩行距離・休憩提案
    actions.ts     並べ替え（canReorder）・Plan B入れ替え・休業の代替
    weather.ts today.ts diff.ts share.ts maps.ts geo.ts availability.ts time.ts labels.ts
  adapters/    SpotProvider / WeatherProvider / TransitProvider の interface と mock/
  generator.ts 旅程生成の差し替え点
  store/       localStorage（キー replan-fukuoka:v2）
  components/ app/   UI（Next.js App Router）
tests/ scripts/e2e-demo.mjs
```

要点:
- すべての時刻は「0:00からの分」。ブロックは `startMin/endMin`（現在値）と `plannedStartMin/plannedEndMin`（計画上の値）を持つ。
- 外部データは adapter 経由（現状モック）。移動時間は「2点間を同期で引ける関数 `TravelEstimator`」を注入する形。
- 旅程操作は不変（`structuredClone` で複製し新しい旅程を返す）。UIは `replan()` の結果（提案）を表示し、確定で `result.after` を保存する。

## 4. アルゴリズムの詳細

### 4.1 旅程生成（`planner.ts`）
- 日の枠（開始/終了）とペース設定:

  | ペース | 開始 | 終了(日帰り/1日目) | 最終日終了 | スポット数目安 | 余白 | 滞在倍率 |
  | --- | --- | --- | --- | --- | --- | --- |
  | ゆったり | 10:00 | 20:00 | 16:00 | 3 | 45分×最大3(120分おき) | ×1.25 |
  | 普通 | 9:30 | 20:30 | 17:00 | 4 | 30分×2(180分おき) | ×1.0 |
  | 詰め込み | 9:00 | 21:30 | 18:00 | 6 | 15分×1(240分おき) | ×0.85 |

- 出発地: 1日目は博多駅、2日目は「宿泊先（天神）」。
- **スコア**: 興味一致 主カテゴリ+3.0／タグ+1.2、人気度×0.8（1〜3）、予算超過 −1.5/段階（贅沢で価格帯2以上+0.4、節約で無料+0.4）、同行者補正（例: カップルの夜景+1.0、家族の自然+0.8）、雨許容度（屋外NG: 屋外−2.0・半屋外−1.0／小雨OK: 屋外−0.5）。
- **配置**: 時間を前進させる貪欲法。候補評価=スコア −0.1×移動分 −0.02×待ち分 −0.8(混雑時間帯。食事枠では−0.4・待ちは0.005/分) ＋時間帯適合（カフェは14:00〜17:30で+0.6、夜景は17:30以降+0.8、屋外・半屋外（夜景を除く）の18時以降−1.0、買い物の19時以降−0.5）−1.5×同日同カテゴリ回数 ＋同エリア連続+0.8 ＋その日まだ屋外・半屋外が無く、雨許容度が「屋外NG」でないとき、17時前の屋外+1.2／半屋外+0.4。Mustは+50。
- 制約: 営業時間内に滞在が収まること、開店待ちは上限（ゆったり・普通40分／詰め込み30分／Must150分）、移動は max(25分, 滞在) 以内（Must除く）、日の終了時刻。
- **食事枠**: ランチ 11:30〜(開始上限13:45)、ディナー 17:30〜(上限19:30)。食事は食事向けスポット（`mealSlots`）から選び、移動は35分以内（Must除く）。ディナー枠だけに指定された店（屋台）にはディナーで+2.0。直前の食事前に長い空きが出る場合はペース上限を1つ超えて追加（`FILLER_GAP=150分`）。
- **Must**: エリア単位でまとめ、滞在時間が偏るよう日に割り当て（1泊2日）。定休日・時間切れで入らなければ警告。
- **Optional**: Must以外の通常スポットの下位1/3（3件以上のとき、最低1件）。
- 生成後に Plan B を付与し、計画上の時刻を確定（`commitBaseline`）。

### 4.2 Plan B 選定（`planb.ts`）
- 必須条件: 屋内／元スポットから直線2km以内／ブロック開始時刻に営業中（滞在は `min(標準滞在, max(30, 元の枠+15))`）／カテゴリ近接度≥0.3。
- スコア: 3×近接度 +1(ユーザー興味) +1.5×(1−距離/2km) +0.2×人気 −0.3×|滞在差|/30 −0.5(混雑) −0.7×予算超過。
- 旅程内の他スポット・他ブロックのPlan B・休業スポットと重複しない。時刻が変わるたびに付け直し（有効なものは維持）。

### 4.3 時刻の再計算（`schedule.ts: recomputeDay`）
- 開始済み（`startMin ≤ nowMin`）は固定。各ブロックの開始 = `max(到着, 計画上の開始, notBefore)`。開店まで待てるなら待つ（上限90分）。
- **遅延**は最初の未開始ブロックの開始に加算し `notBefore` に永続化。**余白は計画上の終了時刻まで延びつつ最短10分まで縮み**、遅れを吸収する。
- **固定時刻**: 固定ブロックの開始は固定時刻そのもの。手前のブロックは、固定時刻から逆算した「最遅の開始時刻」を超えないよう、計画上の開始より前倒しで動く（`floor = min(計画開始, 最遅開始)`）。間に合わなければ `fixed-missed` と不足分を記録。
- 最終便（`endsDay`）のあとに残る予定は `after-last-transport`。スキップ/休業は時間を消費しない（`notBefore` は次のブロックへ繰り越す）。

### 4.4 再計画エンジン（`replan.ts`）
入力: 旅程・イベント・`{dayIndex, nowMin?, removeMustIds?}`。出力: `ReplanResult`（提案）。
1. **イベント適用**: `plan-b`（入れ替え）/`delay`/`closure`（＋代替）/`tired`/`fixed-add`/`fixed-remove`/`margin`/`skip`/`restore`。
2. 再計算 → 最終便のあとの余白を片づけ → （かなり疲れた）近い順に並べ替え。
3. **違反の大きさ（badness）**: 固定時刻・営業時間の違反は 10000＋不足分、最終便のあとは 10000、終了予定超過は「終了＋30分」を超えた分（分）。0 になるまで次を順に実行。
   1. Optional を後ろから削除（削ると badness が下がるものだけ）。
   2. 滞在短縮: 5分刻みで、改善する中で余裕（現在滞在−最低滞在）が最大のブロックを縮める。最低滞在 = `max(15, 標準滞在の半分を5分単位に)`。結局スキップされたブロックは短縮記録から外し、滞在を元に戻す。
   3. 標準を後ろから削除（同様に改善するものだけ）。食事ブロックも標準なので**削られうる**。
   4. なお残れば **Must削除候補**を提示（1手先読み: そのMustを外したとき badness が下がるか。`fixesAll` は全解消するか）。自動では削らない。ユーザーが選んだ Must だけを `removeMustIds` で外して再計算。
4. 結果: `after`（提案）、`steps`（phase=event/reduce/tidy）、`diff`、`violations`、`feasible`、`mustCandidates`、`travelSuggestions`、歩行距離の前後、`notes`。
- 保護: 固定時刻と「疲れた」の休憩（label `rest`）は削減・短縮の対象外。開始済みのブロックは動かさない。

### 4.5 固定時刻（`fixed.ts`）
- 出発すべき時刻 = 固定時刻 − 直前の場所→固定場所の移動時間 − 余裕時間（既定10分）。「直前」= 固定ブロックの手前にある、場所を持つ最後の有効ブロック。
- 次にやること用の逆算 `nextFixedCountdown`（直前のスポットに滞在中なら「ここ」と表現）、通知 `departureNotices`（残り≤30分=before30、≤10分=before10、≤0=over）。
- **メンバー限定**: グループの旅程は変更しない。「ブロック終了 + 固定場所への移動 + 余裕 ≤ 固定時刻」を満たす最後のブロックまでそのメンバーが参加し、以降のブロックを「不在」とする（単調性を仮定）。複数メンバーの不在は名前を結合表示。
- 全メンバーを選ぶ/メンバー1人なら全員に効く固定時刻（ブロック化）として扱う。

### 4.6 「疲れた」
- 休憩挿入位置: 次に始まるブロックの手前（進行中のブロックは動かさない）。
- 少し休みたい: 30分。近く800m以内（直前の場所基準）の屋内カフェ（カテゴリcafe/タグcafe）で、その時間に営業していて旅程で未使用のもの。距離＋0.5×(次の場所までの距離)が最小のもの。無ければ場所なしの休憩（その旨を `notes` に出す）。
- かなり疲れた: 60分（500m以内）、**残りのOptionalを無条件で削除**、`lowWalking`（以降の移動は徒歩600m超を公共交通に）、近い順に並べ替え。
  - 並べ替え: これから行く Must/標準のスポット（食事・余白・休憩・固定は元の位置のまま）の連続区間ごとに、移動の道のり合計が最小になる順を全探索（6件以下）または最近傍法で選び、営業時間/固定時刻に新たな違反が出ない並びだけ採用。時刻の下限は「位置」に付けて引き継ぐ。
  - 提案: 徒歩換算20分以上（道のり≥1.5km）の移動に、公共交通・タクシーの所要時間を併記。
- 匿名: イベントは `{type, level, source?}` のみ。タイトルは「メンバーの1人が休憩を希望（…）」。

### 4.7 推定歩行距離（`walking.ts`）
- 移動1回: 徒歩なら全距離、公共交通なら `min(距離, 600m)`（乗り場までの徒歩）。
- 滞在中（m/分）: グルメ/カフェ 3、屋外の自然・歴史 40、その他屋外 30、半屋外 25、屋内 20、夜景(屋内) 8。固定・休憩・余白は0。
- 目安: ゆったり5km／普通8km／詰め込み12km。提案: 「いままで＋進行中の残り＋次の予定への移動と滞在」が目安を超えるとき、次の予定の前に休憩を提案（既に休憩/余白があれば出さない）。
- **これらの定数は経験則で、根拠となるデータはない。**

### 4.8 その他
- 移動時間: 直線距離×1.3＝道のり。≤1000mは徒歩75m/分、超は公共交通 `10分＋道のり/450m/分`。タクシー `4分＋道のり/500m/分`。
- 共有: `base64url(JSON)`。旅程の状態（スポットはid、固定時刻・メンバー・余裕時間を含む）。旧版(v1)のデコードにも対応。受信側は閲覧のみ。
- 雨: 天気は `WeatherProvider`（モック: 終日10〜20%）にデモ操作の「降り出す」を上書き。

## 7. 自覚している弱点・仮定（正直に）

**データ・生成の質**
1. 座標・営業時間・定休日は記憶ベースの概算。いくつかの店の所在・営業時間は不確か。
2. 貪欲法のため動線は最適ではなく、エリアを行き来することがある（§5.1）。同エリア加点と距離上限で緩和しているだけ。
3. 太宰府に食事向けの店がなく、「梅ヶ枝餅 かさの家」をランチ扱いにして警告を回避している（データ側のごまかし）。
4. ゆったりペースでも、食事前の空きを埋めるため「スポット数目安+1」まで入る。日没は17:30固定。

**再計画エンジン**
5. 優先順位の解釈（標準=中間、余白=吸収材として先に縮む、休憩のみ保護）は仕様の字面と異なる。標準削除ステップは依頼の削減順に無い。
6. 「Optionalを後ろから」は「改善するものだけ」を後ろから探索するため、後ろのOptionalが削られない場合がある。
7. 滞在短縮は5分刻み・余裕最大優先の貪欲法。Must候補は1手先読みのみで、組み合わせ（2件を外せば間に合う等）は探索しない。
8. 食事ブロックを保護していない（ランチ/ディナーが標準として削られうる）。
9. `badness` の重み（10000）は経験則。営業時間違反と終了予定超過の比較などは粗い。
10. `startMin ≤ now` を「開始済み」とみなす単純な凍結。移動中・遅延中の厳密な状態は持たない。
11. 並べ替え（かなり疲れた）の対象は Must/標準の連続区間のみ。食事や余白をまたぐ最適化はしない。時刻の下限は位置に引き継ぐ近似。
12. 例外的に確認なしで反映する変更（`isQuietChange`）があり、「組み直したら必ず確定ボタン」とは完全には一致しない。雨のPlan B切替が2手になり、初回仕様の「ワンタップ」から後退した。

**疲れた・歩行距離**
13. 休憩場所はカフェのみ。近くに無いと場所なしの休憩（デモの太宰府では常にこの状態）。休憩後に長い空きができる。
14. 「徒歩20分以上」は徒歩換算で判定。移動モデル上、実際に20分以上歩く区間は生成されない。
15. 歩行距離の定数に根拠データがない。実測: 生成直後の太宰府の日（普通ペース）は、何も起きなくても**1日の推定歩行が9.5km（目安8km）で目安を超える**（15時時点で6.3km歩行済み・残り3.2km）。つまり目安超過の休憩提案が、崩れていない旅程でも出うる。生成側が歩行距離を考慮していないことも原因（§4.1のスコアに歩行は入っていない）。
16. かなり疲れたは、必要でなくても残りのOptionalを必ず削る（仕様どおりだが乱暴という見方もある）。

**グループ**
17. 複数端末の同期・本人識別・通知がない。共有リンクは静的スナップショット。
18. メンバー限定の固定時刻は「不在」の表示だけで、予約人数や移動手段などの再計画はしない。不在判定は単調性（一度抜けたら戻らない）を仮定。
19. 歩行距離・疲労はグループで1本。個人別の推定はない。

**UI・技術**
20. デモ操作パネルを開いたままだと通知バナーが隠れる（ボタンで自動で閉じるよう緩和）。
21. 保存形式を変えたため、旧バージョンのlocalStorageは読み込まない（キーをv2に変更）。
22. 共有デコード時に `prefs` の型を厳密に検証していない。細工されたリンクでUIが例外を起こす恐れ（Error Boundaryなし）。
23. 旅行日は「直近の土曜」固定。日付入力なし。時刻はすべてローカル分で、タイムゾーン・夏時間の考慮なし。

## 8. 評価者への個別の問い

1. 「標準」を Optional と Must の中間にし、削減順を Optional→短縮→**標準削除**→Must候補としたのは妥当か。それとも依頼どおり標準を扱わない（＝Optionalに含める）ほうがよいか。
2. 余白を遅れの吸収材として先に縮め、「疲れた」の休憩だけを保護する解釈は、「休憩・余白 ＞ Optional」の優先順位と整合しているか。
3. 提案→確定を原則とし、余裕時間変更・固定時刻の削除だけ自動反映にした例外は許容できるか。雨のPlan B切替が2手になったことは、コンセプト（ワンタップ）を損なうか。
4. 固定時刻を旅程内の「ブロック」として時系列に置き、全員向けは連鎖に組み込み、メンバー限定は連鎖の外に置く設計は妥当か（不在判定は単調性を仮定）。
5. Optionalを削る条件を「改善するものだけ」にしたことで、仕様の「後ろから削除」を満たしていると言えるか。
6. 「かなり疲れた」で歩行距離を減らす手段（休憩・Optional削除・近い順・徒歩短縮の見積もり）は妥当か。休憩後に長い空きができる挙動（§5.2）をどう評価するか。
