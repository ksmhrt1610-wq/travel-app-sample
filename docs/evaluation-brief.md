## 1. 概要

**コンセプト**: 「崩れても立て直せる旅程」。旅程を作る時点で、屋外の予定ごとに屋内の代わり（Plan B）を用意しておき、
当日に雨・遅れ・暑さ・疲れ・休業などが起きたら、**差分と理由**を見せて組み直す。軽い変更はワンタップ（またはおまかせで自動）、重い変更は必ず確認。いつでも元に戻せる。
2〜6人のグループが1台を回して希望を集め、3案から投票で決める機能もある。

- 対象: 福岡市内（天神・博多・中洲・大濠公園・百道浜・太宰府）、国内旅行をする大学生・20代の友人グループ。スマホ表示前提。
- 制約: API キー不要（外部データは adapter 層でモック）、データ保存は localStorage、サーバー・DBなし、**LLM 不使用**（旅程生成・再計画・集約はすべてルールベース。LLM に差し替えられる境界は interface だけ用意し、呼んでいない）。
- 技術: Next.js 16（App Router）/ React 19 / TypeScript 5.9 / Tailwind 4 / Vitest 5 / zod 4 / fast-check / dnd-kit / playwright-core（E2Eスクリプトのみ）。
- 規模: `src/core` 6,508行（純粋ロジック）、`src/components` 4,334行、`src/app` 1,341行、`tests` 3,542行（**276テスト**。うちプロパティテスト18件）、`scripts/e2e-demo.mjs` 921行（**188チェック**）。
- 起動: `npm install && npm run dev` → http://localhost:3000（スマホ幅で見る）。`npm test`（276件）、`npm run demo:e2e`（ブラウザでデモを自動確認）。
- 画面: `/` 入力、`/itinerary` 旅程、`/today` 当日モード、`/group` グループ、`/share?s=…` 共有（閲覧専用）、`/debug/crash`（Error Boundary の確認用）。

### スポットデータ（サンプル）
42件（天神10・博多7・中洲4・大濠8・百道浜4・太宰府9）。屋内26・屋外12・半屋外4。カテゴリはグルメ9・カフェ4・歴史13・自然4・ショッピング7・アート3・夜景2。
食事枠に使えるのは8件（`mealSlots`）。休める場所（`restable`）14件。**名称は実在だが、座標・営業時間・定休日は記憶ベースの概算**（画面にも「サンプルデータです」と明記）。
**食事制限への対応（`accommodates`）は8店ぶんの仮データ**（ベジタリアン対応は1店だけ）。糸島のスポットは含まない。

## 3. アーキテクチャ

```
src/
  core/        UI非依存の純粋関数（外部API・localStorageを触らない）
    types.ts       Spot / Block / Day / Itinerary / FixedEvent / Member / Preferences …
    planner.ts     generateItinerary（ルールベース。歩行の予算・食事・Mustの店・食事制限）
    scoring.ts     スコア・カテゴリ近接度（RAIN_PENALTY は満足度とも共有）
    planb.ts       Plan B 選定・付与（旅程内で重複しない。食事の店は食事制限に対応するもの）
    schedule.ts    recomputeDay（時刻再計算・固定時刻の逆算・実績・余白の吸収）
    replan.ts      replan（再計画エンジン）・settle（削減パイプライン）・describeEvent
    cause.ts       Cause（構造化された理由）と ExplanationWriter（テンプレート。差し替え可）
    policy.ts      classifyChange（軽い/重い）・decideApply（モードごとの扱い）
    history.ts     commitResult / undoLast（旅程のスナップショットで完全に戻す）
    fixed.ts meals.ts walking.ts route.ts suggest.ts detour.ts weather.ts today.ts diff.ts …
    schema.ts persist.ts share.ts   zod検証・保存形式v3・共有リンク（8KB）
    parser.ts      EventParser（言葉→再計画イベント。キーワード実装）
    group/         aggregate.ts（集約）satisfaction.ts（満足度）plans.ts（3案）vote.ts schema.ts types.ts
  adapters/    SpotProvider / WeatherProvider / TransitProvider / GroupRepository の interface、mock/、local/
  generator.ts  eventParser.ts   差し替え点
  store/       localStorage（キー replan-fukuoka:v3）・グループ（replan-fukuoka:group:v1）
  components/ app/   UI（Next.js App Router）
tests/ scripts/e2e-demo.mjs docs/decisions.md
```

要点:
- すべての時刻は「0:00からの分」。ブロックは `startMin/endMin`（現在値）と `plannedStartMin/plannedEndMin`（計画上の値）を持つ。実績があれば `actualStartMin/actualEndMin` が優先。
- 外部データは adapter 経由（現状モック）。移動時間は「2点間を同期で引ける関数 `TravelEstimator`」を注入する形。
- 旅程操作は不変（複製して新しい旅程を返す）。UIは `replan()` の結果（提案）を表示し、モードと重さに応じて `result.after` を保存する。**変更の履歴は、変更前の旅程のスナップショットを持つ**ので、元に戻すと完全に戻る。
- 外から入るデータ（共有リンク・保存データ・グループの保存）は、読み込み・保存の前に zod で検証する。

### 4.1 旅程生成（`planner.ts`）
- 日の枠とペース設定:

  | ペース | 開始 | 終了(日帰り/1日目) | スポット数目安 | 余白 | 滞在倍率 | 余白の下限 |
  | --- | --- | --- | --- | --- | --- | --- |
  | ゆったり | 10:00 | 20:00 | 3 | 45分×最大3 | ×1.25 | 20分 |
  | 普通 | 9:30 | 20:30 | 4 | 30分×2 | ×1.0 | 10分 |
  | 詰め込み | 9:00 | 21:30 | 6 | 15分×1 | ×0.85 | 5分 |

- **スコア**: 興味一致 主カテゴリ+3.0／タグ+1.2、人気度×0.8、予算超過 −1.5/段階、同行者補正、雨許容度による屋外の減点。グループ生成では、これに**スポットごとの加点（`spotBias`）**が足される。
- **配置**: 時間を前進させる貪欲法。候補評価=スコア −0.1×移動分 −0.02×待ち分 −混雑 ＋時間帯適合 −同日同カテゴリ ＋同エリア連続 −すでに行ったエリアへの戻り ＋屋外の変化。Mustは+50。制約: 営業時間内・開店待ちの上限・移動は max(25分, 滞在) 以内（Must除く）・日の終了時刻。
- **食事枠**: ランチ 11:30〜(開始上限13:45)、ディナー 17:30〜(上限19:30)。食事は食事向けスポットだけ。**食事制限があれば、全員の制限に対応できる店だけ（行きたい店でも例外にしない）**。見つからなければ、守れない店を入れずに警告。**行きたい店（Mustの食事向けスポット）は食事の枠で使い**、開店まで待ってでも使う（食事を2回入れない）。
- **歩行距離**: 歩行の予算と減点を変えた複数の組み方を作り、ペース別の目安（5/8/12km）の85%に収まるもののうち、空きが少なく食事が揃っているものを選ぶ。その後、動線を改善（2-opt。エリアの行き来が増えないこと）。
- **Optional**: Must以外の通常スポットの下位1/3。生成後に Plan B を付与し、計画上の時刻を確定。

### 4.2 Plan B 選定（`planb.ts`）
必須条件: 屋内／元スポットから直線2km以内／ブロック開始時刻に営業中／カテゴリ近接度≥0.3／**食事向けの店は食事制限に対応**。スコア: 3×近接度 +1(興味) +1.5×(1−距離/2km) ほか。旅程内の他スポット・休業スポットと重複しない。

### 4.3 時刻の再計算（`schedule.ts: recomputeDay`）
- 開始済みは固定。実績（着いた・出発した）があれば、それを優先。各ブロックの開始 = `max(到着, 計画上の開始, notBefore)`。
- **遅延**は最初の未開始ブロックの開始に加算。**余白は遅れを吸収して縮み**、**いま余白の最中なら、その残りが遅れを吸収する**（フェーズ6で修正）。
- **固定時刻**: 固定ブロックの開始は固定時刻そのもの。手前のブロックは、固定時刻から逆算した「最遅の開始時刻」を超えないよう動く。間に合わなければ `fixed-missed` と不足分を記録。
- 食事は食事の窓に収める（超えたら `outside-meal-window`）。終了予定時刻は**30分の許容**あり（超えても、許容内なら違反に数えない）。

### 4.4 再計画エンジン（`replan.ts`）
イベント: `plan-b`（雨・暑さ）／`delay`／`closure`／`tired`／`fixed-add`／`fixed-remove`／`fixed-move`／`margin`／`skip`／`restore`／`add-spot`／`add-rest`／`progress`（着いた・出発した）／`detour`／`heat-rest`／`extend-stay`／`add-buffer`。
出力: `ReplanResult`（`after`＝提案、`steps`（各ステップに `cause`）、`diff`（各行に理由）、`violations`、`feasible`、`mustCandidates`、`suggestions` ほか）。元の旅程は変えない。

`settle()` のパイプライン（違反が解消するまで）:
1. 最終便のあとの余白を片づける／（かなり疲れた）近い順に並べ替え。
2. **Optionalを後ろから削除**（食事・寄り道を除く。改善するものだけ）。
3. **滞在短縮**（食事以外。最低滞在まで。5分刻み）。
4. **標準を後ろから削除**（食事・寄り道を除く）。
5. **食事の調整**: 食事の滞在短縮 → 店の差し替え（元の店から1km以内。食事制限に対応する店だけ）。食事は削らない。
6. なお残れば、**Must・食事・寄り道は「削る候補」として提示するだけ**（自動では削らない）。ユーザーが選んだものだけを `removeMustIds` で外して組み直す。

保護: 固定時刻・休憩・開始済みの予定（**終わった予定は、Plan B の切り替えでも書き換えない**）。理由（`Cause`）は、各削減ステップが「どの問題を解消したか」から決める（`resolveCause`）。

### 4.5 固定時刻（`fixed.ts`）
出発すべき時刻 = 固定時刻 − 移動時間 − 余裕時間（既定10分）。通知は before30 / before10 / over。**メンバー限定**は、グループの旅程を変えず、抜けたあとを「不在」と表示（単調性を仮定）。

### 4.6 「疲れた」
- 少し休みたい: 30分。近く800m以内の屋内の休める場所（`restable`）。いま滞在中の休める場所なら、そこで延長。無ければ場所なしの休憩。休憩を入れる位置は、「失う予定の重み（Optional 1・標準3・食事10・Must100）」が最小になる位置を、次の予定の手前／後など3か所から選ぶ。
- かなり疲れた: 60分（500m以内）、**残りのOptionalを削除**、`lowWalking`（以降は徒歩600m超を公共交通に）、近い順に並べ替え。徒歩換算20分以上の移動に、公共交通・タクシーを併記。
- 匿名: イベントは `{type, level, source?}` のみ。タイトルは「メンバーの1人が休憩を希望（…）」。

### 4.7 推定歩行距離（`walking.ts`）
移動1回: 徒歩なら全距離、公共交通なら `min(距離, 600m)`。滞在中（m/分）: グルメ/カフェ 3、屋外の自然・歴史 40、その他屋外 30、半屋外 25、屋内 20。目安: ゆったり5km／普通8km／詰め込み12km。**定数は経験則で、根拠となるデータはない。**

### 4.8 その他
- 移動時間: 直線距離×1.3＝道のり。≤1000mは徒歩、超は公共交通 `10分＋道のり/450m/分`。
- 共有: `base64url(JSON)`。**8KBまで**。復号は段階的（長さ→形式→版→タプルの検証→スポットIDの存在→旅程の再検証）に行い、失敗の理由を返す。食事（ランチ・ディナー）と食事制限も往復する（フェーズ5・6）。
- 保存: `{version: 3, state}`。旧版（v2）は読み込み時に変換（食事の印を補う）。読めないデータは、確認のうえで削除かバックアップ。確認が済むまでは保存しない。
- 雨・暑さ: 天気は `WeatherProvider`（モック）。雨は強さ（小雨・本降り・強い雨）と許容度で判定。暑さは WBGT 28/31・11〜16時・屋外が対象。

### 4.9 確定のルールと3つのモード（`policy.ts`）
- **重い変更**: Must・標準・食事を外す／Mustを別のスポットに替える／固定時刻が絡む／予算を超える価格帯のスポットが新しく入る／予定の半分以上（かつ2件以上）の中身が替わる／解消できない問題が残る。それ以外は**軽い変更**。
- `decideApply(mode, 重さ, イベント)`: 重い→確認／軽い→手動は確認、提案はワンタップ、おまかせは自動（実績の記録は、手動でも確認なしで記録）。
- 変更は直前10件まで `undoLast` で元に戻せる。

### 4.10 グループ（`core/group/`）
- **集約**（`aggregatePreferences`）: 日程＝全員の共通日（なければ参加者最多の日。欠席者を残す）／予算＝最小（円→予算帯は ¥4,000未満=節約・¥9,000未満=普通）／食事制限＝和集合／雨＝いちばん慎重／ペース＝中央値（偶数で割れたら遅いほう）／好み＝好き+2・どちらでも0・苦手−3の合計／行きたい場所＝2人以上の希望を先にMust、全員（希望のある人）が1件以上Mustに入るよう各人の第1希望を足す（定休日・食事制限で入れられないときは次の希望）。結果に個人の予算額・苦手は含めない。調整ポイントを1行の理由つきで出す。
- **満足度**（0〜100）: `100×Σ(重み×項目)/Σ重み`。好み0.65・行きたい場所0.20（希望がない人は使わない）・ペース0.06・雨0.05・予算0.04。好みは予定ごとの合い方（好き1.0／どちらでも0.5／苦手0.0。食事は苦手の減点なし）の平均。理由の文に具体的な「苦手」は書かない。**重みは、「好みが正反対でも50を下回らず、警告が出ない」問題を直すため、好みの重みを0.55→0.65に上げて調整した値**。
- **3案**: 同じ生成器に、メンバー別の重み（全員均等／満足度の低い人を重く／1人重視）・移動の減点・決まった乱数の揺らぎ・歩行距離の目安にこだわらない案、を渡して候補を十数件作る。食事が揃う→予算内→歩行の目安内の順に絞り、バランス案＝最小満足度が最大／合計いちばん案＝合計が最大／移動いちばん少ない案＝移動時間が最小。バランス案は候補全体から選ぶので、**最小満足度 ≧ 合計いちばん案の最小満足度**が構造的に成り立つ。
- **投票**: 1人1票。全員がそろうまで結果は見せない。同票は主催者の票、主催者の票が同票の案に入っていなければ、主催者が同票の案から選ぶ。
- 「どの案でも、誰かの満足度が40未満」のとき、「希望が大きく割れています」と出す。

### 4.11 EventParser・ExplanationWriter（interface のみ）
- `EventParser.parse(text, {itinerary, ctx, dayIndex, nowMin}) → events[]`。キーワード実装: 疲れた（かなり/へとへと→heavy）・雨・遅れ（分・時間を読む。無ければ15分と仮定して、仮定したことを返す）・寄りたい（スポット名・別名、無ければ自由入力）。読み取れなければ理由を返す。結果は必ず再計画のプレビューを通す。
- `ExplanationWriter.explain(cause, ctx, itinerary) → 文章`。テンプレートで実装。

2. B・Cがリンクを開く → 同じ旅程が見える。ただし**閲覧専用**（「疲れた」ボタン・並べ替えの取っ手・固定時刻の追加は存在しない）。
3. Bさんが自分の端末で `/today` を直接開く → 「先に旅程をつくりましょう」（データは端末ごとの localStorage でAさんのものは引き継がれない）。
4. Aさんが「電車が60分遅延」を確定 → Bさんが同じリンクを再読み込みしても**古い旅程のまま**（リンクは作成時点の写し。再共有が必要）。
5. Aさんが「少し休みたい」を確定 → B・Cの画面には休憩が出ない（**通知は届かない**）。
6. Bさんが「自分の旅程として保存」すると独立したコピーで当日モードを使える。Bさんが「かなり疲れた」を確定しても、Aさんの画面（休憩30分1件のみ）には反映されない。

→ **現状は「3人のグループ機能」が成立するのは1台の画面の中だけ**。複数端末間の同期・本人識別・通知はない。

## 7. 自覚している弱点・仮定（正直に）

**変わったこと（前の版の弱点のうち、改善で解消したもの）**: 食事ブロックを保護していない／共有デコード時に `prefs` を検証していない・Error Boundary なし／雨のPlan B切替が2手／Optionalが削られる理由が閉館時刻でデモが不誠実／生成が歩行距離を考慮していない／太宰府の「ランチ扱い」のごまかし。

**データ・生成の質**
1. 座標・営業時間・定休日は記憶ベースの概算。食事制限への対応は8店ぶんの仮データ（ベジタリアンは1店）。
2. **午後に長い余白（2時間以上）が出る**: デモ旅程に133分、グループのデモに150分前後。原因は、歩行距離の目安を優先して、足すと目安を超えるスポットを入れないため（Mustが歩行の多い屋外のとき顕著）。夕方に開く屋台などを希望にすると強く出る。提案（Optionalの追加など）で埋められるが、生成そのものは埋めない。
3. 貪欲法のため動線は最適ではない（2-optとエリア行き来の減点で緩和）。
4. 太宰府にはディナーの店がなく、太宰府を含む1日はディナーが入らない（警告は出る）。
5. 42件のスポットでは、食事制限・好みの組み合わせによって選択肢が足りない（例: ベジタリアン＋小麦なしの食事は見つからない）。

**再計画エンジン**
6. 優先順位の解釈（標準=中間、食事>標準、余白は先に縮む）は仕様の字面と異なる。
7. 滞在短縮は5分刻みの貪欲法。Must候補は1手先読みで、組み合わせ（2件を外せば間に合う等）は探索しない。
8. 理由（`Cause`）は、各削減ステップが解消した問題から決める推定。複数の原因が重なったときは代表1つ。
9. `badness` の重み（10000）や、終了予定時刻の30分の許容は経験則。
10. 実績がない日は、時刻で「開始済み」を判定する（押し忘れは、計画どおり進んだとみなす）。「着いた」を押さずに時刻が進むと、次の予定が計画時刻に始まったとみなす。
11. 自由入力の寄り道は、座標がないので移動を10分と仮定する。
12. **重い/軽いの分類は、閾値（半分以上かつ2件以上など）が経験則**。「予算を超える」の判定は価格帯（0〜3）の差だけ。

**疲れた・歩行距離**
13. 歩行距離の定数に根拠データがない。「徒歩20分以上」は徒歩換算で判定。
14. かなり疲れたは、必要でなくても残りのOptionalを必ず削る（仕様どおりだが乱暴という見方もある）。

**グループ**
15. **3案の違いが小さい**: Mustが多い日・歩行の目安を使い切る日は、残りの自由度が小さく、3案の違いが午後の1〜2件と夕食の店くらいになる（§5.5）。同じ内容になったときは注記を出す。「3つの選択肢から投票」の意味が薄い場面がある。
16. **満足度は、動かしながら決めたモデル**（重み・閾値の根拠は経験則）。「こだわりなし」の人は中位に張り付く。「40未満」の警告が出るように重みを調整した（§4.10）ので、警告の頻度は、実際の不満の頻度を表さない。
17. **プライバシーは画面上の約束**: 全員の回答（予算額・苦手を含む）が端末の localStorage にそのまま入る。「回答を直す」の本人確認も、画面のダイアログだけ。
18. 複数端末の同期・本人識別・通知がない（やらないこと）。共有リンクは静的スナップショット。グループの確定後に回答を直すと、投票からやり直し。
19. 「誰の希望か」のアイコンは、グループの案の画面だけで、確定後の旅程画面には出ない。
20. メンバー限定の固定時刻は「不在」の表示だけで、予約人数や移動手段などの再計画はしない。歩行距離・疲労はグループで1本。

**UI・技術**
21. デモ操作パネルを開いたままだと通知バナーが隠れる（ボタンで自動で閉じるよう緩和）。`/debug/crash` が本番ビルドにも残る。
22. 旅行日は、通常の入力では「直近の土曜」固定。時刻はすべてローカル分で、タイムゾーン・夏時間の考慮なし。
23. 共有リンクは8KBまで。上限を超える旅程（日数・予定が多い）はリンクにできない。
24. localStorage は、別タブの同時書き込みの競合を解決しない。

## 8. 評価者への個別の問い

1. 「重い変更は、おまかせモードでも自動では反映しない」「軽い変更はワンタップ／自動」という分類（§4.9）は妥当か。閾値（予定の半分以上かつ2件以上、予算超過の判定など）は経験則だが、どこを直すべきか。
2. 食事を「削らず、時刻・滞在・店の差し替えで調整する」とし、食事制限を例外なく守る設計は妥当か。守れる店がないときに、警告だけで食事を入れない挙動（ベジタリアンなど）は誠実か。
3. 「何かを削ったら必ず理由を表示する」を、1つの原因に絞った推定（`Cause`）で満たしているのは十分か。複数の原因が重なるときの表示をどうすべきか。
4. グループの満足度モデル（§4.10）と、バランス案＝最小値最大・合計最大・移動最少という3案の取り方は、合意形成として筋が通っているか。3案の違いが小さい場面（§5.5）をどう扱うべきか（案を増やす／違いが出る軸を足す／1案にまとめる）。
5. 「希望が大きく割れています」の条件（どの案でも、誰かが40未満）と、満足度の重みを警告が出るように調整したことは、許容できるか。
6. プライバシー（予算額と苦手を、本人の入力画面でしか見せない）を、1台を回す前提のUIの約束で満たすのは許容か。最小の追加で実態に近づける方法は何か。
7. 午後に2時間以上の余白が出る生成（§5.1・§5.5）は、「歩行距離の目安を優先する」設計として許容か。余白を埋める提案を、生成の段階に取り込むべきか。
8. プロパティテストが4件の不具合を見つけた。この種の不変条件のうち、足りないものはどれか（1泊2日・複数日の再計画、グループの食事制限と再計画の組み合わせなど）。
9. 最もリスクが高いのに未検証の領域はどこか。
